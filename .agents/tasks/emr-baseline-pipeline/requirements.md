# Requirements — Baseline EMR Serverless Data Ingestion Pipeline (POC)

## Summary

Build a POC-scale, easy-complexity, end-to-end data ingestion pipeline for a banking
customer, running on AWS EMR Serverless with PySpark. The pipeline follows a medallion
architecture extended with a canonical layer (landing → bronze → silver → canonical →
gold), is provisioned with Terraform, orchestrated by AWS Step Functions, and demonstrates
the customer's four key priorities: **FinOps, data security, data lineage, and
tracking/observability**.

The deliverable is a clean, documented, runnable baseline that a solutions team can deploy
and run against AWS to showcase to the customer — not a production-hardened system. Clarity
and a coherent runnable structure matter more than completeness of features. This is the
**baseline** iteration; richer capabilities are explicitly deferred.

**Context constraints:** Development happens on a **local Windows host with NO AWS access**.
Therefore nothing in this task deploys to or runs against AWS — no `terraform apply`, no EMR
job runs, no Athena queries executed here. All AWS resources are expressed as Terraform code
and all Spark logic as PySpark scripts, verified locally only for syntax/structure.

## Functional Requirements

### FR1 — Test data (landing layer)
- Provide exactly **4 banking tables** in the landing layer: `customers`, `accounts`,
  `transactions`, `cards`.
- Small, realistic **synthetic** data (tens to low-hundreds of rows per table) generated by
  a Python script. Formats: CSV and/or JSON.
- Data must include obvious **PII columns** — name, email, phone, national id / SSN-like,
  card number — so masking can be demonstrated downstream.
- Provide a separate script to upload the generated data to the landing S3 prefix.

### FR2 — Medallion + canonical flow
- Layers, each in its **own S3 prefix/path** and its **own Glue database**:
  - **landing** — raw CSV/JSON as delivered.
  - **bronze** — ingested, typed, written as **Parquet**.
  - **silver** — cleansed/validated, written as **Iceberg**.
  - **canonical** — standardized/conformed (naming, formats, PII masking), **Iceberg**.
  - **gold** — business/aggregate marts, **Iceberg**.
- One PySpark job per transition: landing→bronze, bronze→silver (with DQ), silver→canonical
  (with PII masking), canonical→gold.

### FR3 — Data quality checks
- Lightweight, Great-Expectations-style **in-Spark assertions** (no external GE dependency
  required for the baseline): not-null, key uniqueness, referential integrity, value
  ranges / allowed sets, and row-count thresholds.
- Results written as **JSON to an S3 quality prefix**.
- A **FAIL quality gate**: when critical expectations fail, the Step Functions execution
  halts and does not proceed to the next layer.

### FR4 — Custom JSON lineage
- Each Spark job emits lineage as **JSON to an S3 lineage prefix**, capturing: inputs,
  outputs, column-level mapping where easy, row counts, job run id, and timestamp.
- Each job **registers/updates the dataset in the Glue Data Catalog**.
- Baseline uses a **lightweight custom** emitter only — **no OpenLineage/Marquez**.

### FR5 — PII handling (canonical layer)
- Tag PII columns and **mask/tokenize** them in the canonical layer: hash or partial-mask
  card numbers, emails, and national ids (and other PII as appropriate).
- Document which columns are treated as PII and how each is masked.

### FR6 — Observability (logging + audit)
- **Rich structured logging** in every Spark job: job run id, layer, table, row counts,
  durations.
- A run-level **audit/metrics table**: written to an S3 audit prefix and exposed as a
  Glue/Iceberg audit table.

### FR7 — Athena on gold
- A Glue **gold database** plus **example Athena SQL files** querying the gold Iceberg
  tables.
- **Athena workgroup + results bucket** defined in Terraform.

## Non-Functional Requirements

### NFR1 — Scale & complexity
- POC scale, easy complexity. Small data volumes; favor readability and demo clarity over
  performance tuning or production hardening.

### NFR2 — Security
- **SSE-KMS** encryption on all S3 buckets, with the KMS key defined in Terraform.
- **Block Public Access** enabled on all buckets.
- **Least-privilege IAM** for EMR Serverless and Step Functions (scoped roles/policies).

### NFR3 — FinOps
- **Cost-allocation tags** applied via Terraform `default_tags`.
- **S3 lifecycle rules** (e.g., expiration/transition on transient prefixes).
- EMR Serverless cost controls: **auto-stop** of idle application and **maximum capacity**
  limits, with notes explaining the cost story.

### NFR4 — Tracking
- The run-level audit/metrics table (FR6) is the primary tracking mechanism, giving a
  queryable record of each pipeline run.

### NFR5 — Deliverable structure
Project layout must include:
- `infra/terraform/` — all AWS resources, with variables, outputs, and a deploy/teardown README.
- `src/jobs/` — the four transition jobs.
- `src/common/` — logging, lineage emitter, quality/expectations helper, audit writer, Spark+Iceberg session helper.
- `data/generator/` — synthetic data generator.
- `sql/athena/` — example Athena queries.
- `scripts/` — upload and supporting scripts.
- `docs/` or `README.md` — architecture overview (medallion+canonical flow), deploy/run runbook, FinOps story, security story, lineage/quality/observability explanation, Athena how-to, and an ASCII/mermaid diagram.
- `requirements.txt` / `pyproject` for Python dependencies.

## Constraints

1. **Compute:** AWS EMR Serverless with Spark/PySpark. No alternative compute.
2. **IaC:** Terraform under `infra/terraform/`. **Do NOT run `terraform apply`** (no AWS access on this host).
3. **Orchestration:** AWS Step Functions state machine (defined in Terraform) running stages sequentially, invoking EMR Serverless job runs per layer transition, with a **FAIL quality gate** that halts on critical DQ failure.
4. **Lineage:** lightweight custom JSON lineage only — **no OpenLineage/Marquez** in the baseline.
5. **Dev environment:** local **Windows** host with **NO AWS access**. No deploy, no EMR runs, no Athena execution against AWS from here. Verification is limited to local syntax/structure checks.
6. **Technology decisions are locked** for this baseline: EMR Serverless + PySpark, Terraform, Step Functions, custom JSON lineage. Do not deviate without flagging.

## Acceptance Criteria

1. Landing layer defines exactly four tables — `customers`, `accounts`, `transactions`, `cards` — populated by a Python generator producing tens-to-low-hundreds of rows each, including the named PII columns.
2. A separate upload script places generated data into the landing S3 prefix.
3. Four PySpark transition jobs exist (landing→bronze, bronze→silver, silver→canonical, canonical→gold); bronze is Parquet, and silver/canonical/gold are Iceberg.
4. Each of the five layers maps to its own S3 prefix and its own Glue database.
5. The bronze→silver job runs DQ assertions covering not-null, uniqueness, referential integrity, value range/allowed-set, and row-count checks, writing JSON results to the S3 quality prefix.
6. When a critical expectation fails, the Step Functions execution reaches a FAIL state and does not advance to the next layer.
7. Every job emits lineage JSON (inputs, outputs, column mapping where easy, row counts, job run id, timestamp) to the S3 lineage prefix and registers/updates the dataset in Glue.
8. The silver→canonical job masks/tokenizes card numbers, emails, and national ids; PII columns and their masking method are documented.
9. Every job emits structured logs containing job run id, layer, table, row counts, and durations; each run writes a record to the audit/metrics table (S3 audit prefix + Glue/Iceberg table).
10. Terraform defines a gold Glue database, an Athena workgroup, and an Athena results bucket; `sql/athena/` contains runnable example queries against gold Iceberg tables.
11. Terraform enforces SSE-KMS (key defined in TF) and Block Public Access on all buckets, and defines least-privilege IAM roles for EMR Serverless and Step Functions.
12. Terraform applies cost-allocation tags via `default_tags`, defines S3 lifecycle rules, and configures EMR Serverless auto-stop and maximum-capacity limits, with accompanying FinOps notes.
13. Terraform provides variables, outputs, and a README documenting deploy and teardown; no `terraform apply` is executed as part of this task.
14. The repository matches the deliverable structure in NFR5, and the docs include the architecture diagram and the FinOps/security/lineage/quality/observability/Athena narratives.
15. All Terraform validates and all Python is importable/syntactically valid via local checks only (no AWS calls).

## Out of Scope (deferred to later iterations)

- **OpenLineage / Marquez** integration (baseline uses custom JSON lineage only).
- Expanded DQ coverage beyond the listed baseline checks (e.g., distributional checks, anomaly detection, a full Great Expectations suite).
- Richer PII/masking policies (format-preserving encryption, reversible tokenization vaults, column-level access policies, Lake Formation governance).
- Production hardening: CI/CD, autoscaling tuning, DR/multi-region, SLAs, alerting/monitoring dashboards.
- Any actual AWS deployment or execution (`terraform apply`, EMR job runs, Athena query execution) — blocked by the no-AWS-access local host.

## Assumptions

- "Easy level" means straightforward transformations and a small, fixed set of DQ checks — no complex business logic or large-scale performance concerns.
- CSV/JSON choice for landing is at the implementer's discretion per table; both are acceptable.
- Iceberg is managed through Glue Data Catalog as the Iceberg catalog on EMR Serverless.
- A single AWS region and account are assumed; region is a Terraform variable.
- Masking method per column (hash vs partial-mask) is the implementer's choice as long as it is documented and consistent.
